一路护栏，两道闸门

S11 不改变 Agent 做什么，只规定它做不成时怎么办。模型对象和每个工具各套一层代理：调用层管超时、重试、熔断、回退与预算；工具层管循环、顺序和外来文本；回复出门前再过一次结构断言与 L4 审核。预算耗尽时，连请求都不发。

先看泳道图：模型这一层是唯一会花钱的地方，所以三道判断（熔断、额度、超时）都排在真正发起请求之前。

两道闸门，一个出口

横轴是时间，纵轴是层次。接入层先决定这一轮还值不值得开始；模型层在每次真实调用前判断熔断与额度，再管超时和重试；工具层在工具真正执行前拦截循环与顺序违规，并在结果回到模型之前做 L3；输出层只在最终回复出门时出现一次。

4 个预算档位

预算是按天、按 token、全进程一份的池子，不是每会话配额。档位只看一个数：剩余比例。低于 5% 时，run_turn 在 Agent 之前就返回文案——结构化输出的重试会让一条"拒绝"在循环里反复失败，最终 502。

剩余额度档位用哪个模型这一档多做的事
> 50% main 调用方传进来的原模型 不额外加提示，不记降级事件
20% – 50% lite lite_model（未配置则仍是原模型） 每次实际模型与预设不一致时发 model.fallback，reason=budget_tier_lite
5% – 20% minimal lite_model 在系统提示后插入 MINIMAL_MODE_HINT：最多再检索一次，直接简洁作答
≤ 5% fallback 不发任何请求 轮级返回固定文案；调用级若漏网则 BudgetExhausted，同样不发请求
两阶段记账。acquire 先按 ceil(chars / 2.0 × 1.2) 预留，成功后用 provider 报的 input_tokens + output_tokens 结算，失败或取消则整笔退回。重试不重新预留，所以重试不会被重复计费；被拒绝的 acquire 一分不扣。存储写不进去时快速失败开放：记一次 budget.unavailable，之后不再拦任何人。

熔断按名字分开记，模型和工具各用一套

同一个状态机用两次：模型面按模型名计数，工具面按工具名计数（独立实例，kind="tool"）。主模型挂了不连坐 lite 模型，一个工具坏了也不连坐其他工具，更不会把模型降档。半开状态只放一个探针，其余调用继续走下一个候选。

circuit closed →open连续 3 次可重试失败（默认阈值） →half_open冷却 60s 后，第一个调用拿到探针 →closed探针成功：清零失败数，发 circuit.close →open探针再失败：重新计时，所有调用继续跳过

什么算可重试：超时、连接错误、429、5xx。其余错误（400/401/422…）立即释放预留并向上抛，不计熔断失败——重试一次只会得到同样的答案。超时用 asyncio.wait_for 包住单次请求；配置校验保证 request_timeout × (max_retries + 1) < turn_timeout，否则重试还没走完，整轮先超时。

工具面什么算失败：只有 ToolResultState.ERROR（含工具抛异常）计数。业务拒绝是 SUCCESS + ok=false——那是工具按设计在工作，不熔断。熔断打开后，调用不再执行，模型收到 ok=false · circuit_open 的收敛提示，可以换工具或直接回答。

谁在什么通道上被检查

L3 管「别人的话进我的脑子」，L4 管「我的话说给买家听」。工具参数是「我自己决定要做的事」，归 S4 白名单、S10 业务校验和 schema，不归 L3/L4。

事件与计数

日志只写白名单字段：event · tier · model · reason · rule · tool · count · session_id。消息正文、工具输出、模型输出永远不进日志。计数器通过 GET /api/guardrails/status 暴露。

事件计数器什么时候发
model.retry+1同一模型第 n 次重试，带 count
model.fallback+1降档换模型、熔断跳过、重试耗尽换候选——reason 区分三者
circuit.open / close+1失败数达阈值 / 半开探针成功——模型面带 model，工具面带 tool
circuit.skip—候选模型或工具被熔断跳过，只进日志
tool.loop_blocked+1相同工具 + 相同参数第 3 次
tool.sequence_blocked+1本轮已建过草稿 / 已派发过子任务
tool.structure_anomaly—成功 payload 缺约定字段（如 hits），提示写回 payload，只进日志
content.filtered+nL3 命中规则，按命中条数计数
output.guarded+nL4 改写了回复或卡片亮点
reply.assertion_failed+1回复没有 ProductCardList，随后照旧 502
budget.exhausted+1轮级拒绝、调用级拒绝、全部候选熔断
budget.unavailable—额度库打不开，只记一次然后 fail-open

    编号验收项结论代码证据
    S11-1工具连续失败 3 次 → 熔断 open；等待后 half-open；成功一次 → closedPASSGuardRuntime.tool_circuits 按工具名计数：ToolResultState.ERROR 或工具抛异常记失败，成功记成功；open 后调用不再执行，返回 ok=false · circuit_open；冷却后单探针，成功即 circuit.close。业务拒绝（SUCCESS + ok=false）不计失败。
    S11-2401/400（非瞬时）→ 只调用 1 次，不重试；429/超时 → 退避重试PASS_retryable 只放行 TimeoutError / ConnectionError / 429 / 5xx；其余立即抛出，且不计一次熔断失败。
    S11-3主模型重试用尽 → 回退模型接管，发出 model.fallback 事件PASS候选模型链逐个尝试，切换时 metrics.incr("model.fallback") + 结构化日志带 reason。
    S11-4同一工具、同参数、同结果连调 3 次 → 注入收敛提示，不终止PASS第 3 次返回 ok=false + 「请更换查询条件或直接回答」，工具不执行、本轮继续。签名是 tool + 参数 的 sha256（session.py）；参数相同即结果相同，未单独比较结果体。
    S11-5无检索记录直接下单 → 硬拒（返回错误 chunk，工具未执行）PASSS10 的写链：create_draft 先解析每行 SKU 的证据，缺失抛 OrderValidationError("evidence_missing")；工具把它转成 ok=false 结果，绝不落库。
    S11-6工具返回缺 hits 字段 → 只追加「结构异常」提示，不 raisePASSGuardedTool._annotate_payload：ok=true 却缺约定字段时，向 payload 写入 structure_anomaly 提示并记 tool.structure_anomaly；状态仍为 SUCCESS，JSON 仍可解析。
    S11-7token 预算耗尽 → 规则回复收口，不再调模型PASS轮级 turn_allowed_async() 直接返回 rule_fallback_text()；调用级 acquire 拒绝时同样不发请求。
    S11-8每个护栏都有独立开关，关掉后行为回到基线PASSGuardSwitches 十个开关（timeout / retry / circuit / fallback / budget / loop / sequence / structure / content_filter / output_guard），对应 guard_*_enabled 配置项；各层按开关跳过自身行为，/guardrails/status 暴露实际生效的开关。
    8 条全部与代码一致。工具级熔断是这轮补的：复用同一个状态机，但用独立实例按工具名计数，所以工具故障不会把模型降档；模型的整轮 502（S5-2）保持不变——熔断只决定「这个工具还值不值得再调」。
    为什么护栏不写在 prompt 里？prompt 是模型可以忘记的建议，代理是模型绕不过的代码。guardrails_enabled=false 时模型和工具都不包裹，行为完整退回 S10；打开时，主 Agent、子 Agent、摘要调用共享同一份预算与熔断状态，但每个 Agent 有自己的循环窗口——一个买家的重复搜索不会把另一个买家拦下来。
