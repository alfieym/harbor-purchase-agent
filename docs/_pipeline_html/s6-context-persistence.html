两份产物，职责完全不同

最容易搞混的是「流水也是历史，为什么不拿它恢复？」——因为流水是面向人的问答记录（缺工具调用、缺中间状态），而快照是面向 Agent 的完整状态。恢复只读快照。

快照里到底装了什么

不是我们手挑的字段——AgentState 是 AgentScope 自己声明「该保存和加载」的完整状态，我们原样序列化。悬停/聚焦任一层看它承担什么。

恢复的代码路径：一行把状态交还给 Agent

因为 AgentScope 的 Agent.__init__ 就是 self.state = state or AgentState()，而 reply 全程读 self.state.context——没有额外的 memory 需要重建。恢复 = 反序列化 + 传进去 + 重新放行工具。

失败语义：什么会挡请求，什么只留痕

判断标准只有一条：用户会不会以为「已经存好了」。快照是承诺，失败必须 500；流水是旁路，失败只告警。任何失败轮都不落盘。

失败即逐出：为什么异常路径还要 evict

只「不写快照」还不够。失败那轮里，AgentScope 可能已经在 agent.state.context 留下半截消息；而同一个 Session 还缓存在内存里。逐出把这两个隐患一起消掉。

隐患 1

残渣被下一轮写进快照

失败轮留下的半个 user msg / 半个工具调用，会在下一次成功时随整份 context 一起落盘，把「失败轮回滚」悄悄破坏掉。

隐患 2

重试把同一句写两遍

快照写失败后若保留 Session，客户端重试会命中同一个 Agent，同一个 user msg 被追加第二次——把用户被告知「丢了」的那轮又写了回去。

结果

下次访问 = 最后一轮成功

逐出后，下一次 get_or_create 从盘上最后一轮成功的快照重建，内存与磁盘在失败后重新一致。

并发正确性：三道闸

「每会话一把锁 → 不会同时写同一快照」这句话，需要三道闸才真的成立。第三道是代码评审揪出来的缺口，已补。

t0请求 A 进入，拿到会话锁开始 reply。
t1请求 B 同 key 到达，取到同一个 Session，阻塞在锁上。
t2A 工具失败 → evict(key) → 重抛。锁释放。
t3B 拿到锁，但手里的 Session 已被逐出，context 里还有 A 的半截消息。
修复前B 在残渣上继续 → persist 把 A 的残渣写进快照 ✗
修复后锁内复核 is_cached(key, session) 为 False → 回到 get_or_create，从最后一轮成功快照重建 ✓
