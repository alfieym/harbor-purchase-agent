六个指标，各自的边界

指标最容易错的地方不是公式，而是分母和未知值。下面每一行都按当前代码的口径写；括号里是它刻意不做的事。

指标怎么算分母边界行为
NDCG@5 DCG = Σ 1 / log₂(rank + 1)，只有首次命中某个相关 canonical 才得 gain 1 IDCG 取前 min(5, R) 位 重复 canonical 占槽但得 0；只取真实前 5 条，不补位
Recall@5 前 5 条里出现的唯一相关 canonical / 全部相关 canonical R = 相关 canonical 数 R > 5 时 1.0 不可达——这是诚实读数，不是缺陷
返回结果精度 前 5 条里唯一相关 canonical / 实际展示条数 实际返回数（重复占位） 正例返回 0 条记 0 分，不跳过
硬约束违规率 至少有一个展示商品违规的 (case, 约束) 对 / 适用对 适用对数 预算 / 材质 / 投递分开统计；无覆盖 = None，不是 0%
预期无结果准确率 期望空且真的返回 0 条的用例 / 全部期望空用例 空例数 不混入正例的相关性平均；空例也不进 NDCG/Recall/精度
检索耗时 P95 nearest-rank：排序后取第 ceil(0.95 × N) 个值 全部用例的 search 延迟 预热不计分；无样本 → None；n < 20 标记小样本
未知与零是两件事。违规率在没有适用用例时返回 None，P95 在没有样本时也返回 None。若把它们折成 0，一个覆盖率只有 3% 的版本会看起来完美——门禁也就失去了意义。

切分：整条产品线一起走

如果把同一个 canonical 的变体一边放 dev 一边放 test，test 分数就是背答案。切分因此先合并、再分配，最后才看比例。

1 · 合并 union-find

seed_a → canonical X ─┐
seed_b → canonical X ─┴─ 同一组件
seed_c → canonical Y ─── 另一组件

# 组件必须整体进 dev 或整体进 test
# 否则 X 同时出现在两边 → 泄漏

共享任意一个相关 canonical 的种子先并成一个组件。切分的单位是组件，不是种子。

2 · 分配 结构优先

目标 = round(总用例 × 0.30) = 16
实际 test = 15（28.3%）

1. 每个跨 ≥2 组件的桶，
   先拿走一个 test 组件，
   同时保证至少留一个 dev
2. 剩余预算按组件从小到大填
3. 放不下的组件留 dev

先保证每个桶两边都有，再追求比例。跨桶的组件不会为了凑数被拆开。

任一自检失败就拒绝构建，其中最关键的四种是：桶配额不足；正例推不出标签；类目不存在；expected_empty 的 spec 实际能命中商品。构建完成后还有两条全局检查：同一 canonical 不得跨切分，跨 ≥2 组件的桶必须两边都有。最后 cases_sha256 写进 manifest，verify 每次运行前重算。

成对门禁：先问「能不能比」，再问「有没有退」

门禁默认值只容忍噪声，不容忍退步。阈值可在 CLI 上覆盖，但可比性检查没有开关。

检查规则不通过时
同一把尺cases_sha256 完全相同不可比
同一目录catalog_sha256 完全相同不可比
同一口径limit、allow_degraded、索引指纹、用例列表一致不可比
无降级两侧 degraded_case_count == 0不可比
相关性NDCG / Recall / 精度 / 空例准确率，Δ ≥ -0.01failed
硬约束budget / material / delivery 违规率，Δ ≤ +0.01failed
延迟P95 ratio ≤ 1.2x；任一侧无样本则跳过该项failed
为什么不可比时不算指标？两份不同金标、不同目录或不同 limit 的报告，差值没有含义。先判不可比，是为了避免用一个「看起来变好了」的数字掩盖「量的根本不是同一件事」。CLI 在不可比或 failed 时都返回非零退出码。

编号验收项结论代码证据
S12-1六个指标的边界与定义一致PASSmetrics.py 五个纯函数；重复占槽得 0、不补位、R > 5 时 Recall 不可达 1、0 返回记 0、空样本 P95 为 None，均由 test_eval_metrics.py 的 16 条用例钉住。
S12-2金标只由目录事实推导，可复算PASSderive_relevant：概念词全部命中 ∧ matches(product, spec) → canonical_product_id；test_eval_seeds_real_catalog.py 对真实目录重跑，并与提交的 artifact 逐字段比对。
S12-3同一 canonical 不跨 dev/testPASS_assign_splits 先 union-find 合并共享 canonical 的种子，再整组件分配；_check_cases 对泄漏和「跨多组件的桶只有单边」分别报错。
S12-4冻结后的改动可被检测PASSfreeze 写入 cases_sha256，verify_golden 重算并比对；CLI verify 实跑输出 53 cases 与同一哈希；篡改用例后抛 GoldenSetError。
S12-5运行可复现、拒绝降级、不修饰结果PASSrun_golden 每条用例只调一次 search，hits 原样截断；非 embedding 策略默认抛 EvalRunError，allow_degraded=True 才记录；预热延迟单列且不计分。
S12-6不可比与回归都会让门禁失败PASS_incompatibility_reasons 覆盖 7 项；compare_runs 只对可比对做阈值判断；test_eval_cli.py 验证 main 在 verify / compare 失败时返回非零退出码。
四个已知边界，写在结论旁边而不是脚注里。① 投递违规只是诊断：检索接口没有目的地输入，不能作为门禁的硬标签。② test 集只有 15 例，-0.01 的阈值约等于「不能有一例从 1.0 掉到 0.9」，统计噪声偏大。③ category_missing 桶偏弱：不存在的类目会被类目过滤器直接滤空，验证的是「不崩溃」而非召回正确。④ 金标来自字面词匹配，语义改写（用户换个说法）不在覆盖范围内。
当前缺口：还没有真实基线。data/eval/ 里只有冻结的黄金集，没有 baseline.json 或 candidate.json。跑一次真实运行需要约 53 次查询 embedding；在此之前，compare 没有可比对象。
