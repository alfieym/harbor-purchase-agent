API 不再执行 turn

API 只剩三个动作：登记 run、入队、读 journal。执行全部发生在 worker。Redis 只是一声提醒，SQLite 的 run_events 才是唯一真相——提醒丢了，run 不会丢。

一条规则撑起整页：只有仍然 queued 的行，才允许被执行。

一条 run 跨两个进程

四条泳道按谁负责什么分：API 只登记和转播，Redis 只喊人，worker 是唯一执行者。

一次投递，不等于一次执行

队列保证 at-least-once：同一条消息可能被送到两次。系统要做到两次投递、一次执行——靠的不是去重表，而是一条带条件的 UPDATE。

状态的走法

每个 run 从 queued 出发，只会落在四种结局之一；已经 running 的永远不会退回 queued。

迁移谁写的结局为什么这样设计
queued → runningworker · try_claimCAS条件更新 WHERE status='queued'，赢的人才执行
queued → cancelledAPI · request_cancel直接结束还没有写者，API 可以替它收尾
running → finishedworker · execute_turn正常终态与 RUN_FINISHED 同事务
running → failedworker · 兜底 except失败异常只进日志，原始文本不出网关
running → cancelledworker · 读到取消标记取消API 只留一个标记，写者自己收尾
running → interruptedsweeper / worker.stop中断心跳停了，或者进程正在退出
取消为什么要分两种？queued 的 run 还没有写者，API 可以一条 UPDATE 直接结束它；running 的 run 已经有人在写日志，API 只能放一个标记，由持有写序的人写下最后一条事件——否则两个进程会各写一个结局。

没人看着的时候

崩溃不会自己善后。每个 worker 都会定期扫一遍日志，做三件补救。

心跳停了 → 判死

认领时记下 owner 与租约；每次写帧刷新一次心跳。90 秒没有心跳的 running 行改判 interrupted，并补一条 RUN_ERROR(worker_lost)。

queued 太久 → 补喊

登记成功但唤醒丢了：行还是 queued，只是没人知道。超过 15 秒就重新 XADD 并记下已喊过，下一轮不会重复喊。

会话租约 → 回收

一个会话同时只跑一个 turn。租约表不能靠进程内锁，因为两个进程的锁互不认识；过期的租约由 sweeper 清掉。

API 重启不再堵漏：S14 时启动会把遗留的 running 全部改成 interrupted——那是单进程才成立的假设。现在那些行可能正被一个活着的 worker 执行，判断「死没死」只能看心跳，所以这件事交给了 sweeper。

部署：四个进程、两份存储

API 与 worker 是同一个镜像、两个命令；它们只共享 ./data 下的 SQLite 文件和同一个 Redis。

两个命令，一个镜像

API 跑 uvicorn harbor.main:create_app，worker 跑 python -m harbor.worker。没有配置模型时 worker 拒绝启动——一个回答不了问题的进程不该领任务。

滚动发布的收尾

收到 SIGTERM 后，worker 停止领取，把自己正在执行的 run 写成 interrupted(server_restarted)。行不会悬在 running 上，重启后的回放也有结局。

一条回归测试值得记住：跟随者「查日志」和「查状态」是两次读，不是一个快照。worker 可能恰好在这两次之间写完整个结尾——所以看到终态后必须再读一次日志，否则读者会漏掉结局。这条竞争曾被当作偶发失败；现在由 test_a_reader_does_not_miss_events_written_while_it_checks_the_status 固定下来。
四个泳道只有一处共享：SQLite 文件。队列可以丢、可以重复，订阅者可以随时来去；只要那行还在、日志还完整，run 就一定能被重放或补救。
