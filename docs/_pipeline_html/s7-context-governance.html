上下文治理：归档、校验、闸门

S6 让历史不再丢，代价是 state.context 只增不减。AgentScope 自带的压缩是 best-effort：摘要可能编造商品，失败时会直接截断，也没有任何机制阻止超限请求发给模型。S7 在每次 model call 外层加中间件，把「压缩」变成一条可审计、可回滚、有硬上限的流程——这正是「实际没推荐过，却声称之前推荐过 X」这类回答的根因。

下面依次拆：内置压缩缺什么 → 中间件挂在调用链的哪一层 → 四个承诺各自的实现 → 一次被驳回的压缩（可交互重放）→ 它顺手修掉的 S6 回归 → 配置与测试。

内置压缩缺的不是「压缩」，是「保证」

AgentScope 的压缩本身是完整的：切分、摘要、保留尾部、调用 offloader，一样不少。问题在于它的每一条路径都假设「摘要模型会照实写」。

摘要可以编造 gap 1

摘要由模型生成，没有任何机制核对它提到的商品是否真的出现过。一旦编造出一个 SKU，后续轮次的模型会把它当成真实历史继续引用。

失败会静默截断 gap 2

压缩兜底开关默认打开：摘要模型报错就丢掉旧消息，只留一句 "Some earlier messages were truncated"。金额、商品、工具调用一起消失。

没有硬上限 gap 3

压缩是「尽力」而不是「保证」。压完仍超限时，AgentScope 不会拦下请求——超长请求照样发给模型，换来一个 400 或一段被服务端截断的输入。

边界不受保护 gap 4

保留区按 token 比例切分，可能把最近一轮用户消息或一个工具调用/结果对从中间切开——模型看到有调用、没结果。

中间件挂在调用链的哪一层

AgentScope 提供九个钩子；S7 只实现三个，因为只有这三个位置能同时看见需要的信息和需要改的状态。

on_reply 外层

回复入口，包住整轮。做两件小事：清掉上一轮的闸门错误；把 turn_count 写进 middle_context 并 +1。

on_compress_context 压缩层

唯一能在压缩前后同时拿到完整状态的位置：改 context_config、看压缩后的 context / summary、失败时整份回滚。

on_model_call 调用层

拿得到 current_model、真实的 messages / tools 和 count_tokens——闸门只能放在这里。它包在重试循环内部。

四个承诺

用户原话：「旧结果归档指针（不是单纯压缩）」「摘要必须做来源校验」「摘要失败时回滚」「容量是闸门而不是建议」「保护边界：最近两轮 + 商品 + 工具正确调用」。逐条对应到代码。

归档，不销毁 offloader

压缩前把整批旧消息写成 JSON，摘要里留 archive://<session>/<seq> 指针。模型用 read_archive 回查，人直接打开文件。

摘要必须对得上来源 validate_summary

摘要提到的 SKU 必须在「被压缩原文 ∪ 保留尾部 ∪ 上一版摘要」里出现过；提到某 SKU 时，价格数字必须与来源一致。

失败就回滚 restore

摘要报错、校验不过、边界被切——一律恢复压缩前的 context 与 summary，不抛异常；本轮命运交给闸门决定。

容量是闸门 gate

超过 0.85 × context_size 先强制压缩；压完仍超限就抛 ContextCapacityError，路由映射为 507，绝不发给模型。

保护边界 reserve_ratio

最近两轮用户消息及其后全部消息不参与压缩。先抬高 reserve_ratio 让内置切分不碰它，压完再逐条复核。

事实附录 append_protected_facts

校验通过后追加一段机器生成的商品事实。摘要可以写得很概括，但 SKU、标题、金额不会因为概括而消失。

归档：不销毁，只换一个指针

归档是 S7 里唯一「面向未来」的产物：它不参与恢复，只服务追溯。指针写进摘要，所以模型看得见；文件是普通 JSON，所以人看得见。

摘要里的样子 AgentScope 生成

指针由 AgentScope 在 _apply_change 里拼成一个 <system-reminder> 文本块，追加在摘要末尾。我们只负责让它指向一个真实文件。

模型回查的样子 read_archive

只读工具，自带 PermissionDecision(ALLOW)，不弹确认。指针非法或文件缺失时返回 {"error": "归档不存在或无权限"}，让模型放弃回查而不是炸掉回合。

回滚后归档会变成「孤儿」：文件已经写出，但摘要被恢复、指针随之消失，模型再也看不到它。这是有意的——留痕优先于一致。运维可以按会话目录审计这些批次；自动清理不在 S7 范围内。

来源校验：只抓「编造」和「价格错配」

校验对象是模型写的那段摘要文本。刻意不做「覆盖性」检查——要求摘要列全所有商品会让每次压缩都误判回滚；覆盖性由确定性的附录保证。

通过 追加附录

## 任务概述 为用户挑了两款猫包，预算内。 ## 受保护事实（机器生成，未经过模型） - P3472-S1 | 轻便宠物出行包 | ¥567.00 CNY - P5108-S3 | 透气双肩猫包 | ¥899.00 CNY

摘要可以概括、可以省略，但金额和 SKU 从原文逐字抄进附录。重复压缩时整段重写，不会层层堆叠。

不通过 整份回滚

violations - 摘要提到来源中不存在的商品 P9999-S1 - 商品 P3472-S1 的价格与来源不一致（来源 567.00）

任一条命中就恢复压缩前的 context / summary，记 logger.warning。不抛异常，交给闸门判断本轮还能不能继续。

保护边界：先让切分别碰它，再复核它没被碰

「最近两轮」按用户消息定位：取倒数第 2 条 user 消息及其后全部消息。这个区间里同时包含完整的工具调用与结果对。

第一道：抬 reserve_ratio

先量出「system + 保护尾部」的 token 占比，让内置切分至少保留这么多。上限卡在 trigger - 0.01，保证还有东西可压。

第二道：逐条复核

压缩后按消息 id 找回来，再检查每条消息里的每个 block id 都还在——AgentScope 可能在 block 层切分，只查消息 id 会漏。

失败：回滚

边界被切走或工具对被拆 → 恢复压缩前状态。与摘要校验走同一条回滚路径，日志里注明原因。

容量闸门：0.85 是上限，不是建议

每次 model call 都先数 token。没过闸门就原样转发；过了就强制压缩一次、重新数，仍然过不去就让本轮失败。

为什么重试要「立即失败」 retry

on_model_call 包在 AgentScope 的重试循环里。闸门抛出的异常会被捕获并重试——不设标志的话，每次重试都会重新压缩、重新数 token。置位 _gate_error 后，下一轮进入立即抛。

为什么是 507

不是模型失败（502），也不是超时（504），而是「服务端无法在容量内完成请求」。507 语义准确，沿用统一错误信封。

失败后的会话

run_turn 必须显式 except ContextCapacityError: raise 透传，否则会被包装成 502。失败轮不落盘，会话被逐出（S6 失败语义）。

一次被驳回的压缩（可交互重放）

点「下一步」：这一轮在工具返回后超过闸门，中间件强制压缩，摘要却编造了一个 SKU。看归档、状态与闸门三者如何交错。

顺手修掉的两个 S6 回归

压缩会改变 context 的长度和内容，所有「从 context 推导」的旧逻辑都要重审。这两个问题不是 S7 新功能，而是新机制撞出来的老假设。

回归 1：工具失败归因 before

run_turn 原本从 context[context_start:] 找本轮 ERROR 的 tool_result。压缩缩短列表后，下标可能越过尾部，本轮失败被漏判、错误结果当成功落盘。

修复：记录回合开始前已有的 tool_result block id，回合结束后只看「新出现的 id」。

回归 2：轮次计数 before

S6 的 turn_count 靠数 context 里的 user 消息。压缩删掉旧消息后，计数会倒退，流水里的 turn 也跟着错。

修复：计数搬到 state.middle_context["harbor.context_governance"]，随快照持久化；旧快照没有这个键时，首次 reply 用 user 消息数补种。

失败语义

判断标准：这一步失败时，用户看到什么、磁盘留下什么。

显式不在 S7：跨会话归档检索、归档自动清理、摘要质量打分（LLM-as-judge）、修改 AgentScope 内置压缩算法、把归档纳入恢复链路。归档是追溯用的旁路，不是第二份真相源。
