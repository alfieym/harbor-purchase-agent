三作用域偏好记忆：本轮、本会话、长期

S7 已经会注入「会话约束」，但它是隐式的：按线索词从用户原话里猜，只活在当前会话，模型不能主动记、不能改、也不能删。S8 把偏好变成显式、可寻址、可跨会话的记录——每条有稳定 id，三个作用域同时注入，冲突不预先仲裁，由模型自己权衡。

下面依次拆：三个作用域各自存在哪 → 两段式写入 → 长期库怎么保证「事实与向量同生同灭」→ 注入长什么样 → 身份怎么到达工厂 → 工具契约 → 跨两个会话的可交互重放 → 失败语义与测试。

三个作用域只差一件事：记录存在哪

作用域不决定优先级，只决定记录存在哪、活多久。三段注入时并排出现，作用域标签告诉模型「越窄越贴合当下」；真正的冲突留给模型判断。

turn：放在中间件内存 进程内

「这次先看看 2000 以内的」只该影响这一次回复。放在 PreferenceMemory._turn，on_reply 开头清空——不进 state、不进快照、不花钱。

session：放在 middle_context 随快照

它是一个普通 dict，跟着 S6 的 state.model_dump() 一起持久化。换 shopping_session_id 就是新会话；同一会话进程重启也能恢复。待确认队列也放在这里。

long_term：放在 SQLite 跨会话

按 buyer_id 隔离，跨会话、跨进程、重启后仍在。小记录多写，所以选 SQLite 而不是向量库：事实和向量必须同一行。

写入：两段式——先暂存，确认后落库

模型通过五个工具写偏好。turn 立即生效；session / long_term 的 add 只进待确认队列，用户点头后 confirm_preference 才真正写入。只有 long_term 需要向量。

模型不能替用户点头 S8-6

add_preference 只把操作放进 state.middle_context 的 pending 队列，返回 pending: true。队列跨轮、跨快照保留；下一轮注入「还有待确认的记忆操作」，直到 confirm_preference 或 cancel_preference。

去重先于 embedding 省额度

暂存时按 (scope, kind, _preference_key) 比对，重复调用不会产生两条待确认；落库时 (buyer_id, kind, text_key) 唯一索引再兜住跨会话并发。命中就 不调 embedding、不写库。

embedding 在事务之外 无半行

长期 confirm 时先算出向量，再开 BEGIN IMMEDIATE。embedding 失败时事务根本没开始；写失败时操作会放回队列，用户腾出空间后还能重试。

dislike 是结构化记录 代码过滤

kind="dislike" 必须带 material_tags。黑名单不是靠模型自觉：product_search 会把三个作用域的 dislike 合并进 excluded_material_tags，由检索层硬过滤。

失败不拖垮购物轮 SUCCESS + ok:false

所有记忆失败都返回 {"ok": false, ...} 的 SUCCESS chunk。S5 的 ERROR 会映射成 502——一条偏好存不下，不该让整轮购物失败。

长期存储：一行就是一条完整记忆

表结构刻意冗余了 kind 与 scope：S8 写 preference 与 dislike，未来加事实记录不需要迁移。旧库启动时用 ALTER TABLE 补齐后三列。

单条 INSERT / UPDATE 同一行

text 与 vector 出现在同一条语句里。不存在「先写文本、后补向量」的中间态，也就不存在两者不一致的窗口。

查重 + 计数 + 写入同一个事务 S8-3 / S8-5

BEGIN IMMEDIATE 里先查 text_key、再数已用条数、最后 INSERT。两个会话同时写同一句不会各插一条；第 201 条在计数处被拒，并发也插不进去。

version 写在行上 S8-4

每次 update 在 SQL 里 version = version + 1；调用方带着读到的 version 回来，写锁内比对，不一致就抛 MemoryVersionConflict，不覆盖新值。

三层并发保险 跨进程

WAL 让读不阻塞写；BEGIN IMMEDIATE 提前拿写锁，两个进程排队而不是迟到失败；busy_timeout=5000 让它们等。进程内再加一把 asyncio.Lock。

float32 小端 BLOB 可识别

struct.pack 打包，长度 = 维度 × 4。同一行记录 vector_model；换 embedding 模型后，旧向量能被识别并跳过相似检索。

读取：一次 model call 末尾的 UserMsg

注入仍然由 S7 的中间件负责，S8 只换内容：三段并排、带 id 与 version、dislike 单独成行、待确认操作另起一块，每轮重建。它是末尾的 UserMsg，不是 system prompt，也不写回 state.context。

模型实际收到的样子 每次 model call

空的作用域整段省略；三段全空且没有待确认操作时就不注入，回退到 S7 的启发式。只有待确认操作时，第二块单独出现——这正是 S8-6 的可见信号。每段独立限 24 条。

为什么必须在这里注入 S7 闸门

注入发生在 count_tokens 与容量闸门之前。放在别处，注入的 token 不计入 gate_ratio，闸门就会被绕过。

不写回 context 前缀稳定

注入是「这一帧」的视图，不是对话历史。下一轮重建；system prompt 保持稳定前缀，provider 侧缓存不受影响。

显式 session + S7 启发式合并 不回退

merged_session_items 按语义键去重：显式记录优先（它带 id，模型才能改删），启发式只补空缺。S8 之前的旧会话仍能注入约束。

id 与 version 都是给模型看的 可寻址

[长期] pref_bb033c60 以后都只买 500 以内的（v1）——下一轮模型拿着 id 调 update / delete，并原样回传 version；旧值会被 409 拒绝。

不喜欢带材质标签 S8-2 / S8-8

[长期·不喜欢] pref_5e6f7a8b 不要塑料的杯子（材质：塑料）——标签让撤回可追踪；同一份标签被 product_search 当作代码级过滤条件。

待确认块每轮出现 S8-6

只要队列非空，就追加「还有待确认的记忆操作（尚未写入）」。模型因此知道该先问用户，而不是假装已经记住。

身份：不改工厂签名

长期记忆需要 buyer_id，但约 25 处测试用 lambda state=None: … 假工厂。agent_factory(state) 的签名一个字符都不能改。

先写身份，再建 agent SessionStore

get_or_create 加载或新建 state 后，把 buyer_id 写进 middle_context["harbor.identity"]，然后才调用工厂。middle_context 随快照持久化，恢复时身份也回来了。

显式参数优先 CLI

build_agent(runtime, state, buyer_id="cli") 覆盖 state 里的身份。命令行没有 SessionStore，但长期记忆照样能用。

没有身份时 长期关闭

turn / session 照常工作；long_term 返回 {"ok": false, "error": "长期记忆未启用", "retryable": false}，而不是抛异常。部分单测不传 state，这是有意的默认。

工具契约

五个工具都是 is_state_injected=True：AgentScope 把 _agent_state 注入进来，工具的闭包只需要持有 PreferenceMemory，不需要抓 Agent 实例。add 分两段，confirm / cancel 解队列，update 带 version，delete 兼作 dislike 撤回。

跨两个会话的生命周期（可交互重放）

跟着点「下一步」：同一个 buyer 走过两个会话。session / 长期的 add 都先暂存、等确认；看「本轮」在下一轮消失、「长期」落进 SQLite 后在新 Agent 里仍被注入，dislike 被撤回，update 让 version 递增、旧 version 得到 409。

失败语义

判断标准：这一步失败时，模型看到什么、磁盘留下什么、这一轮还能不能继续。
