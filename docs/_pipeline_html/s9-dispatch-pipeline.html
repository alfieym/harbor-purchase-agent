先看下面的三判据：勾掉任意一条，主 Agent 就会自己做——一次 product_search 能完成的，不派。

什么时候该派人

派发不是免费的：每个子 Agent 都是一次独立的 ReAct 回合。省下的是主上下文的噪声，付出的是 token 和延迟。三个勾全亮才值得。

主 Agent 的选择 派发 · task_dispatch

三条都成立：拆成独立任务并发跑，中间过程留在子 Agent 那边，主上下文只收结论和证据。

一次派发的数据流

横轴是三个角色：主 Agent 决定做什么，调度层管并发与核验，子 Agent 只在一个全新上下文里干活。图中只画三判据全部成立的那条路。

并发、排队与超时

一批任务同时起跑，默认最多 3 个在跑，其余排队。批次总预算 75 秒，必须小于一轮请求的 120 秒，否则慢批次会把整轮拖成 504（配置里用校验器挡住）。下图是 4 个任务的示意。

子任务抛异常 整批继续

该任务返回 ok=false · "子任务失败：…"，其余任务照常完成。父 Agent 不会因为一个坏任务拿不到任何结果。

单任务超时 90s

该任务返回 ok=false · "子任务超时"；已经跑完的任务不受影响。

批次预算用完 75s

已完成的结果保留，未完成的任务各自返回 "批次超时未完成"。父回合一定拿得到一份回执。

回执为什么可信

子 Agent 可能记错、也可能编造。核验不用模型，用同一次运行里工具真正返回过的数据做对照。下面是离线脚本里的三条声称。

子 Agent 声称工具实际返回判定
P1 · price_major = 89 P1 · price_major = 89.0 ✓ verified
P404 · “很合适” 从未返回过这个 id ✗ unverified
P1 · price_major = 99 P1 · price_major = 89.0 ✗ unverified
地图与点位。evidence_refs 是逐条声称的判定（点位）；verified_product_ids 是这次运行中工具真正返回过的 id 全集（地图），所以它可能比子 Agent 声称的更宽。父 Agent 只被允许引用地图里的 id；不在图里的，一律标“未核实”。

重启之后，计划还在

账本写进会话快照的 middle_context["harbor.dispatch"]，按 revision 递增，只保留最近 5 批。重启时 build_agent 恢复工具，并把失败 / 未完成的任务点名进系统 prompt。

两批并发时的一帧快照 b1 · b2 都在

middle_context["harbor.dispatch"] = {
  "revision": 2,
  "batches": {
    "b1": {"t1": {"goal": "找饮水器",
                  "status": "ok",
                  "verified_product_ids": ["P1"]}},
    "b2": {"t1": {"goal": "找猫砂",
                  "status": "running"}}
  }
}

revision 的认领与 running 条目的写入在同一个临界区里完成，两个并发调用不会抢到同一个批次号。

重启后的系统 prompt 工具 + 计划

<system-info>上次派发计划（未完成或失败）：
- b2.t1 running：找猫砂
重派、自己做，或向用户说明缺口；
不要当作已完成。
</system-info>

task_dispatch 工具重新注册；计划块来自快照，不依赖模型记忆。status 为 ok 的批次不写进提示词。

S9 七条验收

离线脚本 7/7；真额度脚本（真实模型 + 假 embedding）8/8，含一次“简单请求不派活”的真实判断。

为什么不干脆“总是派”？派发把一次对话拆成多个独立回合：主上下文变干净，但 token 和延迟都变多，而且子 Agent 看不到用户的语气和上下文。三判据就是这条成本线——任一条不成立，主 Agent 自己做，通常一次 product_search 就够了。
